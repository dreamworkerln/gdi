# GDI 0.7: инструкция агенту с Google Drive-коннектором

Для обычного обмена используйте **`agent pull` и `agent push`**. GDI проверяет
данные локально, агент переносит готовые файлы через коннектор. На хосте worker
публикует коммиты, создаёт checkpoint и обновляет пакет для следующего pull.
Агенту нужны Python 3.10+ и Git на Linux. Rclone, pip, Docker и прямое сетевое
подключение GDI к Drive не нужны.

Инструкция относится к agent exchange v1 в GDI 0.7. CLI, worker и runtime должны
быть обновлены вместе. Не применяйте эти команды к runtime 0.6.

## Правила работы

- Работайте в указанном пользователем репозитории и ветке. В существующем checkout
  оставайтесь в текущей ветке, если пользователь не выбрал другую.
- Не создавайте и не переключайте ветки без явного разрешения. Для первого clone
  скачайте пакет именно выбранной ветки; GDI создаст её в новом checkout.
- **Work-ID для обычной работы не нужен.** Не требуйте его и не назначайте
  значение по умолчанию. Коммиты сохраняются с исходными SHA, без squash/rebase.
- Work workflow применяется отдельно: сначала назвать новую `gdi-work/<ID>`,
  объяснить squash при `gdi import` и получить разрешение. Ответ «ID 1» или
  «без разницы» сам по себе не разрешает создавать ветку.
- Соблюдайте разрешения проекта на коммиты, тесты и публикацию. Push не запускает
  CI автоматически. Согласование Work-ID не разрешает эти действия.
- Использование GDI не расширяет задачу до аудита или исправления GDI, коннектора,
  ОС и инфраструктуры. При ошибке сохраните файлы и сообщите исходную диагностику.

## Runtime и первое подключение

Получите готовый `gdi.pyz`, `runtime.json` и эту инструкцию из доверенной папки
`gdi/gdi/runtime/` на Drive. Перед запуском локально сверьте SHA256 и размер
`gdi.pyz` с `runtime.json`; при несовпадении повторите получение runtime.
Исходники GDI, Git checkout, manifests и bundles для установки не нужны.
Проверенный runtime используйте повторно, не скачивайте перед каждой командой.

Пользователь или доверенная конфигурация задают Repository ID и ветку. Не берите
ожидаемый ID из самого проверяемого пакета. Если ID неизвестен, один раз прочитайте
`repository.json` выбранного репозитория, закрепите ID и сообщите о первом доверии.
При расхождении ID остановите обмен и уточните правильный репозиторий.

Каталоги обмена держите вне файлов проекта, например в `/tmp` или `/mnt/data`.
`.gdi` — служебное состояние самого GDI, не место для ваших логов.

```bash
GDI_RUNTIME=/mnt/data/gdi.pyz
WORK_DIR=/mnt/data/checkouts/my-project
EXCHANGE_DIR=/mnt/data/exchange/my-project
REPOSITORY_ID=0123456789abcdef0123456789abcdef
REF=refs/heads/main
```

Пакет ветки находится в папке `agent/` целевого репозитория и называется
`export-<REPOSITORY_ID>-<SHA256 полного REF в UTF-8>.zip`.
Имя вычисляется локально, без обращения к Drive:

```bash
python3 -c 'import hashlib,sys; print("export-"+sys.argv[1]+"-"+hashlib.sha256(sys.argv[2].encode()).hexdigest()+".zip")' "$REPOSITORY_ID" "$REF"
```

Один раз найдите этот файл и общую папку `inbox/` внутри корня GDI на Drive.
Сохраните их Drive ID и соответствие Repository ID/ветки для повторных операций.
Не обходите все репозитории или дерево папок. Если export отсутствует, оператор
должен обновить CLI/worker и опубликовать ветку обычным `gdi push` на хосте.
Не собирайте export самостоятельно из manifests.

## Pull: один файл

Скачайте export по сохранённому Drive ID в raw-режиме коннектора, без base64.
Используйте материализованный локальный файл. Суффикс `.bin`, добавленный
коннектором к локальному имени, не мешает: GDI проверяет содержимое ZIP.

Первое получение в новый каталог:

```bash
python3 "$GDI_RUNTIME" agent pull \
  --package "$EXCHANGE_DIR/export.zip" --repository-id "$REPOSITORY_ID" \
  --destination "$WORK_DIR"
```

Обновление существующего checkout:

```bash
python3 "$GDI_RUNTIME" agent pull \
  --package "$EXCHANGE_DIR/export.zip" --repository-id "$REPOSITORY_ID" \
  --repo "$WORK_DIR"
```

Команда offline: проверяет пакет и Git, применяет fast-forward и записывает базу
для push. Локальные коммиты поверх скачанной базы сохраняются. Грязный checkout,
другая ветка или разошедшаяся история требуют отдельного решения. Автоматических
stash, переключения ветки и переписывания истории нет.

Не скачивайте `repository.json`, checkpoint, manifests и bundles заново для
каждого pull. Не делайте capture и snapshot-build. Проверенный локальный export
можно повторно применять без скачивания, если задача не требует свежего состояния.

## Push: один upload, затем одна квитанция

После разрешённых коммитов подготовьте план в отдельном новом каталоге:

```bash
python3 "$GDI_RUNTIME" agent push --repo "$WORK_DIR" \
  --repository-id "$REPOSITORY_ID" --output "$EXCHANGE_DIR/push-001"
```

Результат — JSON. При `ALREADY_PUBLISHED` обращаться к Drive не нужно.
При `PREPARED`:

1. Загрузите **единственный** файл `files.package.local_path` в сохранённую общую
   папку inbox с **точным** именем `files.package.target_name`.
2. При необходимости сообщите «отправлено worker». Upload ещё не подтверждает
   публикацию коммитов. Worker выбран пакетом export; не спрашивайте пользователя
   о Work-ID или worker ID для этой операции.
3. Дайте worker время обработать очередь, используя локальное ожидание. Затем
   один раз получите JSON по `receipt_path` относительно корня GDI. Если Drive ID
   квитанции неизвестен, нужен отдельный точный поиск этого файла.
4. Примените квитанцию к тому же сохранённому плану:

```bash
python3 "$GDI_RUNTIME" agent push --repo "$WORK_DIR" \
  --repository-id "$REPOSITORY_ID" --output "$EXCHANGE_DIR/push-001" \
  --receipt "$EXCHANGE_DIR/receipt-001.json"
```

Только `PUBLISHED` подтверждает публикацию указанных HEAD и publication ID.
Worker сам выполняет публикацию Git, автоматический/ручной checkpoint,
архивирование и обновление export. Агент не загружает manifest, archive или
checkpoint отдельно. `--full` при подготовке пакета запрашивает full checkpoint
на хосте.

Если квитанции ещё нет, сохраните план и сообщите «отправлено, подтверждение пока
не получено». Не запускайте циклы поиска/опроса Drive; продолжайте разрешённую
независимую работу. Позже можно получить только эту квитанцию. При недоступном
worker пакет остаётся в очереди. Интервал ожидания зависит от настроек worker и
времени публикации. Отсутствие квитанции не означает, что upload нужно повторить.

При `CONFLICT` скачайте свежий export и согласуйте объединение истории. Не
перезаписывайте удалённую ветку. При подтверждённой ошибке доставки повторно
используйте исходный пакет и имя: это сохраняет request ID. Если upload мог
завершиться, сначала получите квитанцию, не создавайте дубликат. При новом HEAD
используйте новый каталог плана. Не удаляйте планы до подтверждения результата.

Если export не содержит маршрута publisher, оператор должен настроить/запустить
обновлённый worker и обновить export. Агент не выбирает worker наугад и не
переходит самостоятельно на старую многошаговую публикацию.

## Бюджет обращений к коннектору

| Операция после первого подключения | Обращения к Drive |
| --- | --- |
| Pull свежего состояния | Один raw fetch export |
| Подготовка push без новых коммитов | Ноль |
| Push и подтверждение | Один upload пакета + один fetch квитанции |

Поиск неизвестных Drive ID добавляет вызовы. Используйте точный поиск и
сохранённые ID; не выдавайте его за бесплатную локальную операцию.
Пакет содержит один полный Git bundle и metadata. Размер Git-истории влияет
на байты, но число manifests не увеличивает число скачиваний.

**Не делайте** обратное скачивание загруженного пакета, свежий listing после
каждого шага, повторные проверки неизменившихся файлов, `prepare/check/accept`,
сборку JSON-ответов коннектора или ручную очистку Drive в обычном pull/push.
Не используйте Google Docs, шифрованные промежуточные документы и собственные
транспорты для переноса результатов инструментов. Проверки содержимого выполняет
GDI локально; повторять их вручную не нужно.

## Отдельно запрошенные CI и work операции

CI, результаты и work lifecycle описаны в `agent-reference.md`, включённом в
тот же проверенный `gdi.pyz`. При необходимости извлеките справочник **локально**:

```bash
python3 -c 'import sys,zipfile; print(zipfile.ZipFile(sys.argv[1]).read("agent-reference.md").decode())' "$GDI_RUNTIME"
```

Читайте только нужную специальную операцию. Справочник содержит прежние
snapshot-интерфейсы; они не заменяют основной pull/push этой инструкции.
Не запускайте CI или work workflow только потому, что они описаны в справочнике.
