# Профилирование команд и обращений к rclone

Для отдельной команды включите журнал JSONL и видимый прогресс:

```bash
gdi push drive --profile-log "$HOME/.local/state/gdi/profiles/push.jsonl" --progress
```

Параметры доступны у `remote add`, `push`, `fetch`, `pull`, `status`, `gc`, команд CI и worker.
Их также можно указать перед командой: `gdi --profile-log PATH push drive`.
Без файла профиля в терминале автоматически показываются только этапы операции,
без подробных вызовов rclone, таймингов и итоговых счётчиков. Тайминги включаются
через `--profile-log PATH` или `GDI_PROFILE_LOG`. `--no-progress` отключает
промежуточный вывод; итог замера при включённом журнале остаётся на stderr.
JSON stdout команд с `--json` остаётся чистым: progress и тайминги идут на stderr.

Чтобы записать подключение и последующие команды в один журнал, в текущем Bash
задайте переменные перед началом работы:

```bash
export GDI_PROFILE_LOG="$HOME/.local/state/gdi/profiles/drive.jsonl"
export GDI_PROGRESS=1
```

Затем выполняйте обычные команды gdi. Если пакет ещё не установлен, запускайте их
из исходников, задав путь к проекту:

```bash
INSTALL_DIR="/путь/к/gdi"
cd "$INSTALL_DIR"
python3 -m gdi remote list
```

Отключение для следующих команд:

```bash
unset GDI_PROFILE_LOG GDI_PROGRESS
```

В конце измеренной команды stderr показывает общее время, количество запусков
rclone, суммарное время этих запусков и путь к журналу. Во время долгого вызова
`--progress` каждые две секунды выводит операцию rclone и длительность ожидания.

Журнал дополняется, а каждый запуск получает собственный `session_id`:

| Событие | Содержимое |
| --- | --- |
| `command_start` | Команда, время UTC и ID запуска |
| `phase_start`, `phase_finish` | Этап и его длительность |
| `subprocess_start` | ID вызова, программа, этап; для rclone — полный список аргументов |
| `subprocess_finish` | ID вызова, длительность, exit code, тип ошибки, размер stdout; для `copyto` — размеры доступных локальных файлов |
| `note` | Пакетное чтение metadata, размер immutable upload или пропуск уже доставленного уведомления |
| `command_finish` | Общее время, exit code, количество и суммарное время вызовов по программам |

Для `push` выделены проверка identity, чтение цепочки публикаций, восстановление
Git-объектов, создание bundle, загрузка bundle, публикация manifest и notification.
Git-вызовы тоже измеряются; их аргументы и содержимое stdout/stderr в журнал не пишутся.
Начало вызова записывается и сбрасывается в файл до запуска subprocess, поэтому
при принудительной остановке процесса остаётся видно незавершённое обращение.

Количество вызовов rclone означает количество запущенных процессов. Один процесс
может выполнить несколько HTTP-запросов к Drive и внутренние retries; этот журнал
не считает HTTP-запросы. Размеры локальных файлов означают размер payload, а не
сетевой трафик. Вложенные этапы перекрываются, поэтому их длительности не складывают
для расчёта общего времени. У параллельных subprocess сумма тоже может превышать
общее время команды.

Для сравнения на настоящем Drive нужны первый `push`, повторный `push` без новых
commits и `push` после нового commit. Сравнивайте отдельно чтения metadata,
листинги, загрузки bundle/manifest и notifications. Оптимизацию следует оценивать
по журналам до/после на одном подключении и сопоставимой истории публикаций.

## Исходный замер на настоящем Drive — 2026-10-09

Пользователь выполнил команды из репозитория gdi через `gdrive:` с включённым
журналом. Ниже данные до оптимизации; время одного обращения заметно меняется
между командами, поэтому сокращение числа вызовов проверяется отдельно от времени.

| Команда | Общее время | Запуски rclone | Время rclone |
| --- | --- | --- | --- |
| `remote add drive gdrive:gdi/gdi --init` | 26.146 с | 6 | 26.058 с |
| Первый `push`, full bundle 266 295 bytes | 67.473 с | 10 | 67.290 с |
| Повторный `push` без новых commits | 29.630 с | 5 | 29.561 с |

Загрузка bundle первого push заняла 6.507 с. Повторный push читал identity
(5.729 с), listing (2.732 с) и manifest (14.997 с), затем повторно создавал
inbox (1.353 с) и отправлял notification (4.750 с).

Изменения обмена:

- `copy` создаёт родительские папки; отдельные `mkdir` перед публикацией manifest
  и notification убраны. См. [команду rclone copy](https://rclone.org/commands/rclone_copy/).
- Immutable uploads используют копирование временного каталога с одним файлом,
  `--immutable --checksum --no-traverse`. Проверка обнаружила, что single-file
  `copyto --immutable` на rclone 1.75.1 local backend перезаписывает отличающийся
  файл; directory copy отказывает с exit 6 и сохраняет старые bytes. Временный
  файл получает конечное имя, обычно через hard link без копирования payload.
- Успешная доставка обычного `repository_updated` записывается через atomic write
  и fsync в `.gdi/notifications/`. При наличии записи повторный push сохраняет
  свежие проверки identity/цепочки и пропускает upload notification. В ключ записи
  входят общий root и все поля notification. При ошибке upload запись не создаётся;
  crash до записи приводит к повторной доставке того же immutable event.
- Несколько manifests выбранной ветки скачиваются одним `rclone copy` с
  `--files-from-raw`, а затем проходят прежние проверки SHA256, schema и chain.
  Используется новая временная папка для каждого чтения; все повторные проверки
  цепочки читают свежие bytes. Другие ветки и bundles в пакет не входят.
  См. [rclone copy](https://rclone.org/commands/rclone_copy/) и
  [фильтрацию по списку файлов](https://rclone.org/filtering/).

Пользовательский повторный push после обновления занял **19.599 с / 4 вызова**:
он создал локальную запись доставки существующей публикации. Следующий повторный
push выполнен агентом на том же Drive: **15.261 с / 3 вызова**, из них rclone
15.215 с. По сравнению с исходными 29.630 с / 5 вызовами общее время этого замера
уменьшилось примерно на 48.5%; это отдельный замер при изменчивых сетевых задержках.
Журнал агента: `/tmp/gdi-drive-after-optimization.jsonl`.

После подключения Drive пользователь разрешил агенту продолжить проверки самостоятельно.
Полный regression: **151 tests, 167.106 с, OK (skipped=10)**. Пропущены opt-in
act/Docker/Drive/service integrations без соответствующих environment flags;
отдельная сквозная Drive-проверка выполнена ниже. Новые проверки покрывают delivery
recovery, свежесть batch metadata, oversized/missing files, immutable uploads
и логирование ошибок/прерываний. Дополнительная адресная проверка запрещает
immutable overwrite даже при одинаковых размере и mtime.

Сквозной прогон выполнен в временных локальных checkout и acceptance-ветке
`gdi-acceptance-9749373b2510` того же `gdrive:gdi/gdi`. Исходный commit
`91e7e801ad74bf9e643cbd12825f7f326b7b5de6` совпадает с первым пользовательским push;
полный bundle отличается именем ref и составляет 266 319 bytes. Временная ветка
с её публикациями была сохранена на Drive; затем пользователь удалил старый remote
перед пересозданием v3. Локальные журналы проверки сохранены.

| Операция | Время | Запуски rclone |
| --- | --- | --- |
| Full push | 44.861 с | 8 |
| Incremental push | 55.331 с | 10 |
| Повторный push с двумя manifests | 13.534 с | 3 |
| Fetch в пустой checkout | 24.295 с | 5 |
| Pull с уже проверенным Git cache | 11.601 с | 3 |

Прогон завершился **PASS**: JSON stdout корректен, публикации имеют ожидаемые
full/incremental kinds, unchanged push сохраняет publication ID, fetch оставляет
HEAD пустым, pull получает exact SHA incremental commit и правильные bytes
проверочного файла. Чтение двух manifests использует один `rclone copy` на каждую
проверку цепочки, включая финальную проверку после upload.
Артефакты: `/tmp/gdi-drive-smoke/gdi-acceptance-9749373b2510/` — `profile.jsonl`,
`results.json`, `verified.json`, stdout/stderr каждой операции.
Regression log: `/tmp/gdi-regression-after-optimization.log`.

Первый push сократился с 10 до 8 вызовов, повторный — с 5 до 3. Приведённые времена
относятся к отдельным замерам, не к стабильной оценке скорости сети. Для incremental
push исходного Drive-замера до оптимизации нет; его время 55.331 с не доказывает
ускорение. Дальнейшее сокращение metadata/API операций остаётся отдельной задачей.

Запись доставки означает завершившийся upload, а не подтверждение обработки worker.
CI requests сохраняют свою прежнюю схему outbox/retry и продолжают публиковаться
по явному запросу. После удаления соответствующей записи в `.gdi/notifications/`
следующий push заново доставит обычное уведомление.
