# Протокол gdi v2 (gdi 0.3, pre-alpha)

## Совместимость и идентичность

Протокол v2 несовместим с v1. Автоматической миграции и изменения существующих remote
нет: используйте новую пустую папку, `remote add --init` и повторную публикацию из
полного локального repo. Нельзя просто изменить version в старом repository.json.

Один rclone URL соответствует одному логическому remote-репозиторию. Инициализировать
его нужно один раз одним клиентом. Проверка пустой папки и upload repository.json не
являются распределённой транзакцией. Незавершённую инициализацию разбирают вручную либо
выбирают новую папку. Последующие клиенты подключаются без --init.

`repository.json`:

```json
{"version":2,"repository_id":"0123456789abcdef0123456789abcdef","object_format":"sha1"}
```

Repository ID закрепляется в локальной конфигурации:

```ini
[gdi "remote.drive"]
    url = gdrive:gdi/my-project
    repositoryid = 0123456789abcdef0123456789abcdef
```

Конфигурация общая для linked worktrees, не коммитится и не переносится обычным clone.
`--repository-id` сверяет известную идентичность при подключении; без него первое
подключение доверяет прочитанному ID. Дальнейшие операции всегда сверяют ID. Имя,
занятое обычным Git remote, запрещено для защиты tracking namespace.

## Файлы и metadata

```text
<rclone-url>/
    repository.json
    bundles/<sha256-of-bundle>.bundle
    updates/<sha256-of-full-ref>/<sha256-of-manifest>.json
```

Manifest полного bundle:

```json
{
  "version": 2,
  "repository_id": "0123456789abcdef0123456789abcdef",
  "ref": "refs/heads/feature/a",
  "head": "0123456789abcdef0123456789abcdef01234567",
  "bundle_sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "bundle_bytes": 4096,
  "bundle_kind": "full",
  "base_publication": null,
  "base_head": null,
  "prerequisites": [],
  "previous": null,
  "nonce": "fedcba9876543210fedcba9876543210"
}
```

У incremental-публикации bundle_kind равен `incremental`, base_publication содержит ID
более ранней публикации этой ветки, base_head — её точный HEAD, prerequisites —
отсортированный список уникальных фактических prerequisite OIDs из header bundle.
Текущий writer всегда выбирает непосредственную предыдущую публикацию базой.
Reader допускает более раннюю базу, но не другую ветку или будущую публикацию.

`previous` описывает порядок публикаций и используется для обнаружения конкуренции.
Он сохраняется также у полного контрольного bundle. `base_publication` описывает
зависимость Git-объектов; у полного bundle она отсутствует. Эти поля не взаимозаменяемы.

Сериализация: UTF-8 JSON, sort_keys=True, separators=(",", ":"), trailing LF. ID
публикации — SHA256 точных bytes manifest, включая LF. Nonce — случайный UUID hex.
SHA256 полного ref используется для пути, сам ref сохраняется без потерь. Все поля
обязательны; неизвестные поля, дубликаты ключей и неподдерживаемые версии отвергаются.

HEAD и prerequisites — 40 lowercase hex: протокол явно ограничен SHA-1 repositories.
Принимаются unfiltered SHA-1 Git bundles формата v2/v3 с одним advertised ref.
Версия gdi-протокола и версия формата файла Git bundle — независимые понятия.

## Push и контрольные bundles

Первый push ветки создаёт полный bundle. Обычный следующий push делает:

```bash
git bundle create source.bundle refs/heads/BRANCH ^BASE_HEAD
```

Base HEAD берётся из предыдущей принятой публикации, не из последнего CI job.
Новый commit должен быть потомком предыдущего HEAD. При одинаковом HEAD обычный push
ничего не публикует. Данные нового bundle проверяются локально до upload.

Git может записать несколько prerequisites даже при одном исключении ^BASE_HEAD,
особенно после merge. Writer сохраняет фактический список из header. Reader сверяет
его с metadata и проверяет, что каждый prerequisite входит в объявленную базовую
историю. Затем выполняются git bundle verify, импорт с fetch.fsckObjects, проверка
advertised ref, точного HEAD, типа commit, ancestry к previous HEAD и LFS/gitlinks.

После каждых N обновлений от полного bundle создаётся новый полный. Default N=20:
между полными бывает не более 19 дельт. `--checkpoint-every N` действует только для
текущего push; N=1 всегда создаёт полный bundle при новом HEAD. `--full` создаёт полный
контрольный bundle, в том числе для текущего HEAD, если последняя публикация была
дельтой. Повтор --full для уже полного того же HEAD — no-op.

Порядок публикации: проверить видимую цепочку → создать/проверить bundle → повторно
проверить цепочку → upload bundle → upload manifest последним → проверить новую
цепочку → сохранить проверенные объекты и retaining ref в локальном кеше.
Обе загрузки используют rclone copyto --immutable.

Bundle без manifest не выбирается. Неудачный upload может оставить orphan bundle.
Upload manifest не атомарен на всех backends: видимый повреждённый/частичный manifest
даёт отказ, а не произвольный выбор старого tip. Дождитесь uploader и повторите fetch;
при устойчивой ошибке сохраните remote для диагностики и разберите незавершённый файл.

## Fetch и локальный кеш

Кеш каждого repository ID находится в собственной `.gdi` основного worktree:

```text
<main-worktree>/.gdi/cache/<repository-id>/repository.git/
    objects/
    refs/gdi/publications/<publication-id>
```

Это отдельный bare repo, а пользовательский repo по-прежнему должен иметь worktree.
Каждый retaining ref создаётся только после полной проверки публикации и импорта
объектов. Незавершённый импорт без этого ref не является принятой публикацией.
Автоматическая Git maintenance кеша выключена. Runtime dependencies по-прежнему нет.

Reader сначала проверяет всю видимую metadata-цепочку выбранной ветки. Затем идёт от
tip по base_publication назад до проверенной кешированной публикации или полного
контрольного bundle. Недостающие bundles применяются вперёд по зависимостям. Новый
клиент стартует с последнего полного bundle; промежуточные старые bundles до него
для bootstrap не нужны, но их manifests остаются частью metadata-цепочки.

Каждый downloaded bundle проверяется по SHA256, byte size, prerequisites, ref и HEAD.
Полный проверяется в пустом временном bare repo. Для дельты временный repo читает
объекты кеша через локальный read-only alternate; его refs/config остаются отдельными.
Новые объекты импортируются в кеш только после проверки. Кеш не получает permanent
alternates и не зависит от временного repo после его удаления.

Кешированная публикация принимается по retaining ref, точному HEAD и проверке
connectivity объектов. Уже проверенные удалённые bytes повторно не скачиваются:
это опирается на неизменяемость опубликованных bundles/manifest. Изменение удалённого
bundle под старым именем может быть не замечено клиентом с корректным кешем, но новый
клиент отвергнет его checksum. Metadata всё ещё читается при каждой операции.

Если у принятой кешированной публикации обнаружены неверный ref или нарушенная связность объектов,
кеш сбрасывается и восстанавливается из remote. `gdi cache clear NAME` позволяет
сбросить его вручную без сети, изменения рабочих файлов, refs, конфигурации и Drive.
Очистка действует на весь кеш этого repository ID, включая другие подключённые имена
с тем же ID. Проверенные промежуточные этапы переживают restart и не загружаются заново.
Connectivity-проверка кеша не пересчитывает хеши всех локальных blobs при каждом вызове;
при других локальных ошибках очистите кеш вручную и повторите загрузку.

Лишь после восстановления целевого HEAD объекты импортируются в пользовательский
repo и tracking ref обновляется с проверкой прежнего значения. До этого отказ не
меняет пользовательские refs или объекты; служебный кеш может уже содержать базы.
FETCH_HEAD не используется, tags автоматически не импортируются.

## Pull, конкуренция и восстановление

Pull запоминает branch/HEAD/статус дерева, выполняет fetch, проверяет ancestry и
повторно проверяет branch/HEAD/чистоту дерева/незавершённые Git-операции. Применяется
проверенный OID через git merge --ff-only --no-autostash. Пустую ветку можно заполнить
первым pull. Отказ из-за расхождения может оставить новый fetched ref для изучения.

Локальный flock сериализует CLI-команды gdi и работу кеша между linked worktrees.
Он не блокирует обычный Git и не является удалённой блокировкой. Не изменяйте worktree
и служебный кеш другими процессами во время gdi. Hooks выключены, GIT_* overrides
очищаются; в cache/quarantine также отключена global/system Git config.

Поддерживаются последовательные push в один ref. Неизменяемые цепочки выявляют два
продолжения одного previous, несколько корней, пропущенных предков и циклы. Время и
порядок listing не выбирают победителя. Проверки до/после upload не являются CAS:
поздний конкурент может создать конфликт после ранее успешного ответа другому клиенту.
Конфликт разбирается вручную; сохраните обе истории, согласуйте Git-ветку и заведите
новый remote. Не удаляйте произвольный manifest для выбора желаемого tip.

Отсутствующая/испорченная нужная дельта вызывает явную ошибку, а не выполнение CI или
запрос к выключенному controller. Клиент с проверенной историей может опубликовать
новый --full; читатель начнёт восстановление с него. Предшествующие manifests должны
оставаться доступны. Устаревшие bundles можно удалить ручным `gdi gc`; автоматической
очистки remote и локального кеша нет.
Для принудительного полного push достаточно полной локальной Git-истории, включающей
точный previous HEAD: служебный кеш и прежние bundles могут отсутствовать. Полный
bundle проверяется в пустом quarantine, включая ancestry к previous HEAD, перед upload.

## Ручной GC bundles

`gdi gc NAME` читает metadata всех опубликованных веток и показывает план.
`--keep-checkpoints N` (по умолчанию 2, минимум 1) сохраняет последние N полных
checkpoint каждой ветки и все публикации после старшего из них. Дополнительно
сохраняется рекурсивное замыкание по `base_publication`: v2 допускает базу раньше
непосредственной предыдущей публикации. Набор нужных bundle hashes объединяется
по всем веткам. Все manifests, repository.json и bundles без manifest сохраняются.

При `--apply --quiescent` перед удалением проверяются все сохраняемые публикации:
скачивание и SHA256/size/header/ref/HEAD, импорт в чистые временные Git repositories,
проверки ancestry/prerequisites и полный fsck. Рабочие файлы, refs и существующий
кеш пользователя не изменяются. После проверки повторно сверяются repository ID,
точные bytes metadata и список/размеры bundles. При наблюдаемом изменении удаление
не начинается. Удаляются только отдельные запланированные `bundles/<sha256>.bundle`
через rclone deletefile. После удаления состояние сверяется ещё раз.

Старые отсутствующие bundles вне сохраняемого набора допустимы: это необходимо для
повтора частично завершённого GC. Отсутствующий сохраняемый bundle, неизвестные пути,
некорректные metadata, конфликтующие цепочки или ошибка проверки отменяют удаление.
При сбое удаления часть кандидатов уже может быть удалена; оставьте обмен на паузе
и повторите GC. Metadata не переписывается, protocol v2 остаётся совместимым.

Это не online GC: `--quiescent` требует согласованной остановки push/fetch/pull/GC
на всех остальных клиентах, включая уже выполняющиеся чтения. Проверки снимков не
дают CAS и не исключают гонки после последней проверки. Все участники должны соблюдать
паузу. Сохраняемые checkpoints не означают автоматический fallback при повреждении
последнего полного bundle. Операции со старыми commits и ветками работают через
сохранённую Git-историю; GC не удаляет commits из полных bundles.

Полный порядок эксплуатации: [gc.md](gc.md).

## Границы

Нет подписей, проверки авторства, защиты от полного rollback удалённой истории, CAS
на Drive, multi-writer serialization и переноса LFS/submodule payload.
Кеш и metadata растут; GC вручную удаляет устаревшие bundles, оставляя orphan bundles.
Listing и чтение всей metadata-истории происходят при каждой операции; уменьшение
этих запросов — отдельное улучшение. Сетевые retries/timeouts
обеспечивает rclone; permanent errors и исчерпание retries дают ошибку gdi.


## Автономный CI

Начиная с gdi 0.3 CI использует отдельный namespace `ci/` и `ci_version:1` без
изменения Git protocol v2. Request связывает exact publication/ref/head и локальный
профиль worker; result и artifacts проверяются независимо от Git fetch.
См. [ci-protocol.md](ci-protocol.md). Обычный pull не имеет CI gate, а
`pull --passed --job ID --profile full` применяет точно SHA выбранного PASS.
Apply-GC проверяет отсутствие queue markers и неполных CI jobs; старый gdi 0.2.1
нельзя использовать для GC CI remote. CI artifacts сохраняются отдельно от bundles.
