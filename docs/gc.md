# Ручная очистка remote bundles

GC в gdi 0.3 удаляет устаревшие упаковки Git-истории из папки remote. Commits,
manifests, настройки remote, рабочие файлы и локальный кеш остаются. Protocol v3
не меняется. GC никогда не запускается автоматически после push или CI.

## Команды

```bash
gdi gc drive
gdi gc drive --keep-checkpoints 3
```

Без `--apply` это только план: ветки и их HEAD/Publication IDs, сохраняемые полные
checkpoint, кандидаты с размерами и общим объёмом, количество сохраняемых orphan
bundles. План читает и проверяет metadata, но не скачивает Git bundles. Он не
подтверждает успешное восстановление данных; оно проверяется при применении.

Параметр `--keep-checkpoints` — положительное число, по умолчанию 2. Ветка в команде
не указывается: GC учитывает **все** опубликованные ветки данного Repository ID.

## Что сохраняется

Для каждой ветки сохраняются N последних полных checkpoint и все публикации после
старшего из них. Если полных checkpoint меньше N, сохраняются все имеющиеся.

При N=2:

```text
full A → delta B → delta C → full D → delta E → full F → delta G
└────── кандидаты ────────┘  └──────── сохраняются ────────────┘
```

Если сохраняемая дельта ссылается на базу раньше D, GC сохраняет также эту базу и
все её зависимости до полного bundle. План может оставить больше N полных checkpoint.
Набор bundle hashes объединяется по всем веткам: нужный хотя бы одной ветке файл
не удаляется.

Сохраняются все manifests, даже относящиеся к удалённым bundles: reader проверяет
целую metadata-цепочку. Bundles без manifest тоже остаются — это могут быть следы
прерванных загрузок. Очистка таких файлов требует отдельной политики.

Новый клиент получает историю от последнего полного bundle и нужных баз дельт.
Сохранение второго checkpoint даёт запас данных для ручного восстановления;
автоматического fallback при повреждении последнего checkpoint пока нет.

## Применение

1. Согласуйте паузу обмена на всех машинах: агент, host пользователя, другие clones,
   фоновые задачи. Дождитесь доставки всех CI results, остановите worker, новые
   push/fetch/pull/GC и дождитесь завершения текущих.
2. На одной машине просмотрите `gdi gc drive`.
3. Примените очистку с той же политикой хранения:

```bash
gdi gc drive --apply --quiescent --keep-checkpoints 2
```

4. Дождитесь exit 0 и сообщения `GC complete` либо `Nothing to delete`, затем
   возобновите обмен.

`--quiescent` — ваше подтверждение согласованной паузы. Это **не удалённый lock**:
gdi не останавливает остальные машины. Локальный flock защищает только операции
gdi в текущем Git common directory. Без `--quiescent` применение отвергается.

Перед первым удалением GC скачивает **все сохраняемые публикации каждой ветки**
в отдельные временные репозитории. Проверяет bundle SHA256, размер, header,
prerequisites, ref, HEAD, ancestry и целостность Git objects. Существующий локальный
кеш не используется и не очищается. Если восстановление не прошло хотя бы для
одной ветки, ни один кандидат не удаляется.

После проверки повторно сверяются Repository ID, точные metadata и список/размеры
bundles. Наблюдаемое изменение remote отменяет удаление. Каждый кандидат удаляется
отдельно через `rclone deletefile`; результат каждого удаления выводится в stdout.
После удаления состояние проверяется ещё раз. Проверки не исключают гонок с
несогласованным клиентом, поэтому пауза обязательна. Хранение двух checkpoint или
удаление только старых по времени файлов не заменяет эту паузу.

## Ошибки и повторный запуск

- Повреждённая metadata, конфликт цепочки, неизвестные файлы/каталоги в `branches/`
  или `bundles/`, неверные размеры и отсутствующие нужные bundles останавливают GC.
- При ошибке до первого удаления кандидаты остаются на месте.
- При сетевой ошибке во время удаления часть кандидатов уже может отсутствовать,
  даже если сервер не успел подтвердить последнее удаление. Сохраните паузу и повторите
  команду: план строится заново, отсутствие устаревших bundles допустимо.
- Если после очистки обнаружено изменение remote или backend ещё показывает удалённый
  файл, проверьте состояние и повторите GC до возобновления обмена. При повреждении
  metadata не обходите проверки ручным удалением manifests.

План не сохраняется как разрешение на будущее удаление: каждый `--apply` заново читает
remote и выполняет проверки. Для отчёта можно перенаправить stdout/stderr в локальный
лог. Удаление manifests и сокращение metadata-цепочки не входят в эту версию GC.

## Место на Google Drive

Программа показывает размер bundles, удаляемых из активной папки remote. Это не
измерение свободной квоты Google Drive. По умолчанию rclone Drive использует
`use_trash=true` и отправляет файлы в Корзину; gdi наследует настройки rclone,
не включает безвозвратное удаление и не очищает Корзину автоматически. Если у вас
уже настроено `use_trash=false`, применяется эта настройка.

GC удаляет лишние упаковки, но последний полный bundle продолжает содержать всю
достижимую историю ветки. Старые commits и добавленные в историю большие файлы
остаются внутри него. Полное удаление такой истории — отдельная операция с другими
гарантиями, а не задача этого GC.


## CI jobs

В gdi 0.3 `--apply` отказывает при legacy queue pointer, неполном request/ready v1/v2,
отсутствующем terminal result или отсутствующем объявленном artifact. Даже готовый
result с оставшимся queue marker должен сначала быть подтверждён worker и удалён
из очереди обычным recovery. Не удаляйте claim/queue вручную ради обхода защиты.
CI snapshot повторно проверяется до удаления bundles и после операции.

Поддерживаемая отмена с cancel.json блокирует GC, пока нет подтверждённого
CANCELLED. Обычный поздний PASS отменённой попытки не считается завершением.
Если подтверждение находится в `ci/jobs/JOB_ID/cancelled/`, GC учитывает marker,
этот result и наличие его объявленных artifacts; исходные файлы остаются историей.
Withdrawal старого worker с `worker_cancellation_supported:false` не доказывает
остановку и сам по себе не превращает незавершённое задание в terminal.

Старые gdi 0.2.1 этой защиты не имеют: обновите все клиенты, прежде чем применять
GC на remote с CI. Все manifests сохраняются; worker может восстановить старый
job SHA из нового полного checkpoint с проверкой ancestry. CI logs, chunks, results,
artifacts и локальный spool этим GC не очищаются. Их retention — отдельный этап.
