# gdi

gdi — мост между AI-агентом, который пишет код в изолированном контейнере,
и обычной разработкой на компьютере владельца. Через Google Drive агент получает
Git-историю, сохраняет изменения и отправляет их на CI. Проверки выполняются
на отдельном Linux-компьютере; результат и логи возвращаются тем же путём.

## Зачем это нужно

В среде агента, для которой создавался gdi, нет произвольного доступа к сети:
нельзя просто клонировать проект с GitHub или отправить изменения по SSH.
Устанавливать пакеты тоже нельзя. Контейнер может быть пересоздан с потерей
локальных файлов. Зато есть коннектор Google Drive.

Из этих ограничений и вырос gdi:

- **История переживает контейнер.** Git-репозиторий публикуется на Drive в виде
  bundles и метаданных. В новой сессии агент восстанавливает его и продолжает
  работу. Сохраняется только то, что действительно опубликовано на Drive.
- **Агент сам проходит цикл исправлений.** Постоянный worker на компьютере
  владельца проверяет точный commit через act и Docker. Агент получает прогресс,
  полный лог и PASS/FAIL, исправляет причину падения и отправляет новый commit.
- **Человек выбирает, что принять.** Публикация агентом не меняет рабочую копию
  владельца. Для получения конкретного проверенного commit есть `pull --passed`;
  для законченной работы из checkpoints — отдельный операторский импорт.

Проект вырос из ручного обмена Git bundles и скриптов запуска worker. Теперь
получение истории, публикация, очередь проверок и приём результата собраны
в один инструмент.

## Как проходит работа

```text
Агент в контейнере <---> Google Drive <---> Компьютер владельца
  код и commits          история,           worker: act + Docker
  исправления            задания CI,        проверка точного commit
                         логи и результаты
```

Агент получает проект, работает в своей ветке и публикует checkpoints. По запросу
запускается CI: worker восстанавливает опубликованный commit в отдельном checkout
и выполняет workflows из его `.github/workflows`. При FAIL агент читает лог,
исправляет код и повторяет цикл. Когда работа готова, человек получает выбранный
результат в свой репозиторий.

SHA256, неизменяемые файлы публикаций и `verified: true` нужны, чтобы этот цикл
опирался на проверяемые данные. GDI проверяет, что полученные история, лог
и результат CI относятся к заданному репозиторию, публикации и commit.
Одной надписи PASS в статусе недостаточно. Это проверка целостности и соответствия
данных; качество кода и достаточность проверок по-прежнему требуют оценки.

Обмен Git-историей работает и без CI. Обычный CLI использует rclone, а агент
в песочнице — коннектор Drive: GDI готовит файлы и проверяет локальные снимки,
коннектор скачивает и загружает данные.

## С чего начать

Текущая версия — **0.4.0, pre-alpha**. Нужны Linux, Python 3.10+ и Git.
Сторонних Python-библиотек во время работы нет. На компьютере владельца нужен
настроенный rclone; для CI дополнительно нужны act и Docker. Агент может запускать
GDI из исходников или готового `gdi.pyz` без установки пакетов и rclone.

Первоначальная настройка описана в [INSTALL.md](INSTALL.md). После установки
и настройки rclone новый проект публикуется так:

```bash
gdi init -b main my-project
cd my-project
# Добавьте файлы проекта, затем создайте первый commit.
git add .
git commit -m "Initial commit"
gdi remote create drive gdrive:gdi/my-project
gdi push
```

`drive` — имя подключения в GDI, `gdrive` — имя настроенного remote в rclone.
Для каждого проекта выбирайте отдельную пустую папку на Drive. Для существующего
Git-проекта выполните `gdi init` в его корне; для подключения уже созданного remote
используйте `gdi remote add drive URL` вместо `remote create`.

На другом компьютере с rclone:

```bash
gdi clone gdrive:gdi/my-project my-project-copy --branch main
```

Агенту с коннектором нужна [инструкция для агента](docs/agent.md): она описывает
получение runtime, восстановление проекта, checkpoints, обмен и проверку CI.

После CI в той же ветке можно получить выбранный PASS в чистую рабочую копию:

```bash
gdi pull drive --passed --job JOB_ID --profile full
```

Команда применяет точный проверенный SHA через fast-forward. Обычный `gdi pull`
получает опубликованную вершину ветки без проверки PASS. Законченную work-ветку
оператор принимает через `gdi import`: это отдельный squash workflow, описанный
в [docs/work.md](docs/work.md). PASS исходного checkpoint не становится
автоматически PASS нового squash-коммита.

## Границы применения

Запись в одну ветку должна быть последовательной: распределённой блокировки
и атомарного Git push через Drive нет. Force push, tags, удаление обычных веток,
shallow/partial clones, публикация submodules и LFS pointers не поддерживаются.
Подробности и правила восстановления — в [справочнике](docs/cli.md#ограничения).

SHA256 не подтверждает авторство. Папка Drive и исполняемые workflows должны быть
доверенными: worker запускает код проекта с доступом к Docker Engine.
