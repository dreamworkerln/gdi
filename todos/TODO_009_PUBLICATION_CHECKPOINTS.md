## Проблема и цель

Сейчас `previous` связывает все manifests ветки, включая полные bundles.
Обычный reader проверяет цепочку от первой публикации; clone из новой среды
должен получить все manifests, хотя Git-объекты восстанавливаются от последнего
полного bundle. GC удаляет старые bundles, но не сокращает metadata chain.
Стоимость свежего восстановления растёт с числом push. Кеш и объединение
всех manifests в один файл снижают накладные расходы, но не ограничивают объём
метаданных, обязательный для обычного восстановления с нуля.

Цель: ограничить обязательный объём актуальных метаданных интервалом полных
публикаций, независимо от общего числа исторических публикаций. Архив читается
по запросу исторической операции, а не при каждом обычном clone/fetch/push.

## Согласованные решения

- Полный bundle сопровождается контрольной точкой метаданных: это один
  протокольный результат полной публикации, а не отдельный ручной этап.
- Правило одинаково для `gdi push --full`, `gdi push -f` и автоматического выбора
  полного bundle по `--checkpoint-every`. Начальная full-публикация тоже
  самодостаточна. Полная публикация того же HEAD не теряет свой смысл.
- Эквивалентный offline путь `agent prepare/check/accept` создаёт и проверяет
  тот же результат; агент не пересобирает metadata вручную.
- Старые manifests сохраняются в архиве. Обычное восстановление читает последнюю
  подтверждённую контрольную точку и только последующие manifests.
- Repository ID, существующие Git-коммиты и их SHA сохраняются. Squash, rebase,
  пересоздание remote и удаление пользовательской истории не входят в переход.
- Оператор сообщил, что старые клиенты будут обновлены. Совместимость со старыми
  клиентами для этого перехода не требуется; CLI, worker и runtime должны
  одинаково понимать новый контракт до его использования на remote.
- Согласование этих решений не означает deploy, миграцию remote, запуск тестов
  или commit/push. Реализация и активация требуют соответствующих указаний.

## Инварианты и границы

- Контрольная точка — явно определённая граница доверия. Новый reader не должен
  заявлять полную проверку древней цепочки, если он использовал checkpoint.
  Просто пропускать отсутствующие `previous` в текущем v3 validator нельзя.
- Checkpoint связывает идентичность репозитория, ветку, публикацию, HEAD и hash/размер
  полного bundle. Схема, адресация и выбор актуальной точки должны проверяться.
- Создающий checkpoint клиент проверяет исходное состояние и fast-forward;
  читатель по-прежнему проверяет bundle hash, Git-объекты, ref и точный HEAD.
- Сбой/потеря подтверждения при upload, публикации checkpoint или архивации
  не должны лишать читателя последнего подтверждённого состояния. Повтор операции
  должен использовать сохранённые immutable artifacts, не плодить новые версии.
- Конкурирующие публикации/контрольные точки нельзя скрыть выбором удобной вершины.
  Старый план не должен незаметно публиковаться в уже закрытый участок истории.
- Нельзя переносить неограниченный рост в обязательный listing всех checkpoint
  или в один всё увеличивающийся индекс. Нужно учитывать лимиты коннектора,
  размер metadata и количество сетевых вызовов, а не только число downloads.
- Исторические Publication ID и CI requests/results сохраняют смысл; необходимые
  архивные metadata и bundle dependencies не удаляются обычным checkpoint.
- Work/import/retirement, GC, log и exact-SHA CI должны учитывать архив. Обычный
  clone не должен загружать их исторические зависимости без необходимости.

   проверку через реальный коннектор; отдельно согласовать публикацию/активацию.

## Критерии приёмки

- [ ] Ручная и автоматическая full-публикации создают пригодный checkpoint;
  incremental-публикации продолжают активную цепочку.
- [ ] При фиксированном интервале K свежий clone после 50, 500 и 5000 публикаций
  имеет ограниченный K объём обязательных актуальных manifests/listings и
  сетевых запросов; не читает всю архивную историю. Измерения и окружение сохранены.
- [ ] Восстановленный Git HEAD и reachable история совпадают с исходными;
  обычный режим не вводит squash или смену Repository ID.
- [ ] Hash/identity/ref/HEAD mismatch, неполный listing, испорченный checkpoint,
  конфликтующие продолжения и stale plan дают отказ с понятной диагностикой.
- [ ] Fault injection на границах каждой записи/публикации: прежнее подтверждённое
  состояние остаётся читаемым либо новое уже полностью подтверждено; retry безопасен.
- [ ] Исторические CI, архивные exact publications, work import/retirement,
  log и GC сохраняют заявленный контракт и dependencies.
- [ ] Переход существующего remote сохраняет данные и ID; неподдерживаемый
  формат отклоняется старым/необновлённым участником, без автоматической очистки.
- [ ] Раздельно зафиксированы software validation, реальные connector checks
  и фактическая активация; отсутствие проверок не объявляется PASS.
